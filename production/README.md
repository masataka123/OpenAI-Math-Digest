読者は当該分野の博士院生以上・研究者。目的は「どのように解いたか」と、結果・仮定・入力のつながりを伝えること。

3. [表示形式の必須仕様](FORMAT_CONTRACT.md)。カタログは034、記事の骨格はSchnell、文献案内は033 Orbifold Iitakaを見本とする。
4. [記録の仕様](RECORDS.md)、[引用の共通仕様](CITATIONS.md)、[公開チェックリスト](RELEASE_CHECKLIST.md)。

新しいカタログに034・033の過去の担当範囲、公開許可、固定の図数、略号をコピーしない。現在のユーザー指示を優先し、変更した共通仕様は版と変更点を残す。進行中のカタログには採用版を記録し、共通仕様を更新しただけで既存記事を一括書き換えない。

このセットは制作指示と雛形である。引用の整合性は自動検査するが、全項目の自動検査や数学的な妥当性の認定をするものではない。既存の検査で扱えない項目は担当が確認して記録する。

## 論文数に応じた運用

| 収録状況 | 担当 | カタログページ |
|---|---|---|
| 1本 | カタログ本部が記事も担当。通常は分担しない | 短い概要、1本の記事への入口、日英PDF、原典・確認範囲。論文間の総括図や選択UIは省く |
| 少数 | 本部で順次執筆、または負荷に応じて分担 | 公式順一覧と必要な接続だけ。無関係な論文を一つの証明経路にまとめない |
| 多数・長文 | 原稿の長さ、方法、直接入力、既存記事の有無を見て可変人数に分担 | 公式順一覧、内容に応じた複数の経路、結果単位の接続 |

- 担当人数、カタログの「流れ」の数、図数はそれぞれ別に決める。3担当・3分類・3図を標準値にしない。
- 1本でも記事の主定理・証明・引用の品質と日英PDFは省略しない。長く難しい原稿も、初稿は核心に絞って最大60分で区切る。
- 1本の場合のPDFは短いカタログ案内＋記事1本の2章。記事の証明図をカタログにも複製する必要はない。
- 1本でも他カタログ・外部文献への入力／利用関係はあり得る。重要な接続だけ本文や短い一覧で案内し、同じカタログ内の論文間依存と混同しない。
- 複数本でも確認できた接続がなければ関係図を作らない。「未調査・未記録」と「調べた範囲で直接利用を確認できなかった」を区別する。

## 役割と変更範囲

| 担当 | 成果物・責任 | 通常の変更範囲 |
|---|---|---|
| 記事担当 | 原典読解、日英記事、TeX/SVG、出典・時間・未確認記録 | 割り当てられた `drafts/catalog-NNN/<paper-id>/` |
| カタログ本部 | 台帳、分担、受領ごとの統一編集、接続照合、日英総括、引継ぎ | `coordination/catalog-NNN/`、当該カタログの `drafts/`。並行中の記事は担当に編集を返すか編集担当を交代してから触る |
| サイト本部 | 共通表示、サイト登録、PDF生成、全体検査、公開反映 | `src/`、`public/`、`scripts/`、共通文書・設定、統合後の全体 |

同じチャットが複数の役割を担ってよい。1本では記事担当とカタログ本部を兼任する。PDFはサイト本部が責任を持ち、カタログ本部は引継ぎに「PDF待ち」を必ず残す。

共通ファイル、とくに `site.mjs` と `pdf-editions.json` の書き込みはサイト本部で順番に行う。記事本文は担当フォルダを分けて並行作業できる。共有作業場のブランチを切り替えたり、他担当の未コミット変更を消したりしない。Git競合では双方の差分を照合し、ours/theirsで一括選択しない。

この文書自体は新しいチャット作成・他チャットへの送信・公開の依頼ではない。それらは現在のユーザーによる指示の範囲で行う。すでに依頼された操作について重ねて確認を求める必要はない。

## 制作の順序

1. **棚卸し**：Git状態、公式番号・分野・英語表記・掲載順、原稿版・ページ・ハッシュ、既存記事の有無を確認。[RECORDS.md](RECORDS.md) に沿って台帳を作る。同じ論文が既存カタログにあれば同じpaper IDと記事を再利用し、原稿版の違いを記録する。
2. **構成と担当**：単論文／複数論文の構成、担当、変更範囲、PDF担当、公開範囲を `coordination/catalog-NNN/README.md` に記録。[START_CATALOG.md](START_CATALOG.md) と [WORKER_TEMPLATE.md](WORKER_TEMPLATE.md) を使う。
3. **記事初稿**：1本ごとに読解・執筆・図・確認を合わせ最大60分。開始・締切・終了を記録。下限なし。未完成なら未完成と明記し、自動延長しない。担当に次の記事があれば本部の確認待ちで止めず進む。
4. **受領ごとの編集**：日英、見出し、定理、図直後の説明、独立した引用段落、根拠、未確認の記録を点検する。全記事が揃うまで不統一を放置しない。修正一覧は記事ごとにまとめ、編集時間は初稿と別に記録する。
5. **カタログ案内**：記事の用語と結果を照合してから、確認できた接続を総括にする。単論文では短い入口にする。原典の供給結果→利用箇所→目的→必要な仮定を記録する。
6. **サイト組込みとPDF**：サイト本部が共通の文字・図・日英切替・ナビゲーションを使って登録。日英PDFを生成し、カタログ冒頭にリンクを配置する。
7. **検査と公開**：[RELEASE_CHECKLIST.md](RELEASE_CHECKLIST.md) に証拠を記録。公開が依頼範囲なら反映し、Actionsと公開URLを確認する。公開が範囲外なら公開前までの成果物と残作業を明示する。

## 完了の区別

- **初稿引渡し**：担当成果物と未確認・未完成を渡した状態。時間上限で区切っただけでは記事完成ではない。
- **内容編集済み**：日英記事・図・総括・出典の必要な編集を終えた状態。PDF・公開は別に記録する。
- **公開準備完了**：必須成果物、サイト組込み、日英PDF、必要な検査が揃った状態。
- **公開確認済み**：依頼された公開を実施し、公開サイトでも反映を確認した状態。

数学的確認は別軸である。入力定理の記述と使用箇所の照合、証明の一部の読解、全証明の独立検証を区別する。保留の接続は断定しない。形式検査やビルド成功を数学的正しさの認定にしない。

## 既存実装を使う範囲

- 記事：`src/lib/render-draft.mjs` と `article-structure.mjs`、共通CSS・図拡大部品を使う。引用だけの独立段落が出典表示になる。[雛形](ARTICLE_TEMPLATE.md) を参照。
- カタログ：新規には `CatalogMarkdownOverview.astro` を使い、単論文の省略条件とカタログ別データを確認する。033・034は既存の表示部品を維持しているため、引用・出典欄は公開前に比較する。033専用の `CatalogDraftOverview.astro` を番号だけ置換して使わない。
- PDF：登録済みカタログごとの生成は実装済み。[PDF手順](../scripts/pdf/README.md) を使い、別の冊子生成系を作らない。
- 図：既存の `diagrams` / `diagrams:catalog` はすべての新規原稿を自動検出するものではない。担当は自分の図だけを生成する手順を記録し、無関係な図を上書きしない。
