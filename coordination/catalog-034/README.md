## 全窓口の共通仕様

1. 最初にプロジェクトの `AGENTS.md` と `PROJECT_PLAN.md` を読む。ユーザーとの会話は日本語、記事は日本語・英語。
2. 読者は当該分野の博士院生以上。中心は「どう解いたか」。標準用語の長い定義や読者向けQ&Aは不要。
3. 既存のLA・Schnellの記事の構成・用語・図の書式を基準にする。記事は以下の順序にする。
   - 短い導入：何を示し、どの方法で到達するか。
   - 主要なTheorem / Corollary：原典の番号・順序・仮定・結論に準拠。原稿版・ページを付ける。
   - 証明概略図と、その直後の文章による説明。主要な帰着・場合分け・非自明な適用を述べる。
   - 外部入力とカタログ内の接続：供給元の結果、得られる内容、利用箇所、適用仮定を記す。
   - 原典への入口と確認範囲：読んだ証明箇所、照合した直接入力、未確認箇所を分ける。
4. 図は既存のTeX/TikZの書式を参考にする。箱には操作を示す見出しと必要な数式、矢印には使う内容と補題・定理・ページを付ける。図を数式だけにしない。日本語版の図は日本語。引用・説明・矢印が重ならない余白を確保する。
5. 図の枚数と文字数は機械的に固定しない。主要結果に到達する経路が追える分量にする。長い原稿の全節を同じ深さで要約しない。
6. 原典の主張と編集側の確認を分ける。Introductionや既存のカタログ要約だけから証明を組み立てない。核心の証明本文と、直接引用する外部結果の記述・適用箇所を読む。外部結果の証明全体は再帰的に追わない。
7. 引用を結果単位にする。主定理、独立した道具、帰結、条件付きの前提、背景を区別する。論文同士の相互引用をそのまま循環論法と扱わない。
8. 原稿を確認して既存のカタログに誤り・不足を見つけた場合は、担当フォルダの `catalog-changes.md` に根拠付きで提案する。共通カタログを直接変更しない。
9. 参照commitは `adc7f1241b42e322a6451854ab7e4b4c146bf78a`。034内のPDFはGitHubの `blob` 閲覧URLを使い、自動ダウンロードになるraw URLを公開用の引用に使わない。GitHubではPDFのページ断片に依存せず、表示する引用名にページを書く。
10. 原典の仮定・例外・条件付き結果を短縮によって落とさない。全証明の正しさを認定した表現をしない。「内容の指摘・修正提案」へのリンクは追加しない。

## 保存先と受け渡し

各担当は自分の4論文について、次のフォルダ内に成果物を保存する。

```text
drafts/catalog-034/<paper-id>/
  article.ja.md          日本語の記事本文
  article.en.md          対応する英語の記事本文
  diagrams/             図のTikZ原本・必要なプリアンブル・生成したSVG/TeX
  sources.json          原典版、直接入力、引用番号、読んだページ、未確認点
  status.md             開始・終了時刻、進捗、実施した確認、本部への申し送り
  catalog-changes.md    カタログの修正・追加候補（ある場合）
```

図の引用URLは実際のリンクにする。画像を作れたか、TeX生成・SVG生成・目視確認のどこまでできたかをstatusに記録する。図の実装や生成に詰まった場合も数学的な図の仕様とTikZ原本を残し、時間上限内で本部へ引き渡す。

記事の原稿は後で本部が共通表示へ組み込む。各窓口が独自のAstroレイアウトや共通スクリプトを作る必要はない。`src/`、`public/`、`scripts/`、package設定、`PROJECT_PLAN.md`、他の担当フォルダは本部の管理対象。Gitのcommit・checkout・push、公開操作、追加のチャットやサブエージェントの作成も各窓口では行わない。

外部入力の調査は担当外論文でも可能。成果物を担当フォルダへ記録し、別の窓口の記事完成を待たず、固定版の原典を参照する。

### sources.jsonに残す情報

- `paperId`, `sourceCommit`, `sourceUrl`, `sha256`, `checkedOn`。
- `statements`: 定理名・番号・仮定・結論の記述箇所（PDFページ）。
- `proofPassages`: 実際に読んだ証明の節・命題・ページ。
- `dependencies`: 供給元URLと結果・ページ、利用先の箇所、供給内容、照合範囲。
- `unresolved`: 未確認の接続。未確認項目があることと、依存関係がないことを混同しない。

すべて埋めるために推測しない。原典に番号がなければ節・ページ・式を記録する。

### status.mdの最小形

```markdown
# <paper-id>
- 担当: A / B / C
- 開始: YYYY-MM-DD HH:MM JST
- 終了: YYYY-MM-DD HH:MM JST（進行中は未記入）
- 状態: 調査中 / 執筆中 / 本部確認待ち / 時間上限で区切り
- 成果物: ファイル名
- 確認済み: 読解・日英対応・図の生成と目視等、実際に実施したもの
- 未確認・申し送り: 箇条書き
```

1篇ごとに最大60分（原典確認・執筆・図・担当内確認を含む）、下限なし。まとまれば早く終了する。60分で未確認点と成果物を保存して次へ進む。未完成部分を完成と記載しない。本部の編集・組込み・最終検査の時間は別途記録する。

## 本部の担当

- 担当表・共通仕様を管理する。指示の変更は全窓口へ同じ内容を伝える。
- 各窓口のstatusと成果物を読み、1篇ずつ用語・記号・図の配置・引用・日英対応を統一編集する。
- 主要な仮定、証明の接続、引用箇所を重点的に再点検する。全外部証明の再検証へ拡張しない。
- 共通のサイト表示へ組み込み、記事への導線と034の接続データを更新する。
- 既存のLA・Schnellを保ちながら、ビルド・リンク・数式・図・日英・スマートフォン表示を検査して公開する。
- 全14篇の一次概説が揃った段階で、記事とカタログの整合性を横断点検する。初稿の不足が残る場合は、公開数と残る課題を正確に報告する。
